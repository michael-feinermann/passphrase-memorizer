# Windows CUDA 1.0.1 internal audit

14 October 2026. This supplements the original CPU audit. Scope: NVIDIA CUDA inference, full model/KV placement, graphics-kernel access, NVIDIA memory policy, signed native dependencies and the updated Windows supervisor. This is an internal engineering review.

## Validation state

The final dual-signed candidate passed the 12-check UI fixture, live LPAC/CUDA isolation fixture, cancellation after GPU load/READY and real Gemma 4 31B generation. All fixtures use fixed public words and emit only status/placement metadata. The generated story is not written to the test log. Installation verification is pending closure of the currently open older app.

Final signed candidate timings: UI 0.60 seconds; isolation 8.09 seconds; cancellation 0.5 seconds after READY (27.12 seconds including signature verification/model loading); full generation 25.1 seconds (29.01 seconds including package verification). The final signed generation attested 41,622 CUDA model operations and zero CPU model operations. Cancellation is tested after GPU context/model/KV setup; this does not attest that a particular kernel was running at the instant of cancellation.

The exact tested candidate was archived without rebuilding. ZIP `Passphrase-Memorizer-1.0.1-Windows-CUDA-x64.zip`: 474,022,153 bytes; SHA-256 `e7b3caa624629197593e8f39ca079419fcb1462f1f063160c3a66dc128dde076`. Both detached archive signatures, the full extracted bundle inventory and all 20 payload signatures passed. Independent C reference tools also reproduced the archive's SHA3-512 and Skein-1024-1024, alongside SHA-256. ## GPU enforcement

llama.cpp remains pinned to `8e1642198dcd4e408f8776222d6ae31b74d01187`. CUDA is statically linked; CUDA runtime is static; two unmodified NVIDIA-signed cuBLAS DLLs are separately inventoried and dual-signed. Dynamic backend plugins, HTTP/server/tools, OpenMP, Vulkan and unified-memory environment overrides are disabled. All tensor buffers, including token embeddings normally retained on CPU, are explicitly assigned to CUDA. Every tensor/layer/output and memory-breakdown entry is checked. A scheduler callback rejects CPU model arithmetic before dispatch; reshape/view metadata performs no arithmetic.

Actual allocation placement is checked before READY, before any prompt byte, and refreshed after generation before a bounded public proof frame and story are accepted. Model and KV CPU bytes must be zero; all model-operation counters must be CUDA. Host input/metadata is separately bounded to 16 MiB. Free VRAM is checked before loading and against the actual model/KV/compute allocation plus a reserve. Insufficient GPU resources fail closed instead of switching to CPU.

Before child creation, the trusted parent configures and reloads the exact executable's dedicated NVIDIA profile with `Prefer No Sysmem Fallback` (setting `0x10ECECC9`, value 1, current profile location 0). No global profile or unrelated app setting is changed. NVIDIA documents this setting as disabling shared-memory fallback. The setting and extended DRS function IDs are hidden APIs: their mappings are corroborated by the installed NVIDIA App, the original Profile Inspector source and actual fresh-session driver readback on version 617.42. Missing/unsupported APIs or mismatched readback abort before the child or prompt.

The profile helper leases the canonical System32 `nvapi64.dll`, verifies cached/offline Authenticode trust and NVIDIA identity, loads its absolute path and checks the actual loaded module path. Correct ABI sizes, explicit Unicode strings and session/module lifetime are required. Profile data contains public executable setup metadata, no input or story. The app's own preferences still contain only language, dimensions and model path.

An independent live NVIDIA App check selected the installed runner's exact absolute path and displayed `CUDA-Speicher-Fallback: Kein Fallback bevorzugen`; a fresh DRS session then confirmed status 0, setting `0x10ECECC9`, value 1 and explicit current-profile location 0. Adding the program in NVIDIA App had moved its association into a new default profile. The production helper's fresh lookup before every launch resolves this new association and reapplies/verifies the required value; it does not rely on a cached profile name. Two unneeded dedicated build-probe profiles were removed after checking their exact one-app/one-setting contents.

## Isolation and expanded trust

The sole creation-policy change permits Win32k graphics-kernel calls required by CUDA/WDDM. The previous restriction returned CUDA_ERROR_NO_DEVICE despite a working RTX 4090. LPAC, exactly one `registryRead` capability, explicit readonly ephemeral profile and Storage registry ACLs, protected private registry canary, one-process kill-on-close job, signed file leases and inherited-handle allowlist remain. No network or extra capability was added. Public GPU allocation/memset/readback and all original live network/file/registry/child-process denials passed together after removing only the graphics syscall restriction.

Every production launch repeats denial probes before sending a prompt, including external/loopback IPv4/IPv6. A public 2x2 CUDA matrix multiplication must also yield the expected result. NVIDIA drivers, CUDA libraries and Win32k now expand the trusted attack surface; this is explicitly required by GPU execution. Their vendor signatures do not substitute for review of their opaque internals. Administrators, malware running as the user and a compromised OS remain outside the asserted boundary.

After the final candidate fixtures exited, the cleanup snapshot found zero workers, public canary directories, owned AppContainer profile directories/mappings, Storage registry roots or private registry canaries. The model, shipping candidate, archive extraction, installed payload paths, cuBLAS files and their checked ancestors retained no individual temporary AppContainer ACEs. Three unresolved historical development ACEs for one package SID remain only on the ignored `.build/windows-runtime` directory, its `dist` directory and build-output runner; their source could not be conclusively attributed, so they were not removed. They do not grant that SID access to the model or shipping bundle.

## Memory limits and sources

Full GPU model/KV residency does not mean the Windows process consumes zero RAM. UI, tokenization, sampling, scheduler metadata and temporary bounded upload staging require RAM. The public fit harness sampled peak physical working set around 1.5 GiB during upload and about 436 MiB afterwards; its much larger virtual private commit includes CUDA/WDDM bookkeeping and is not a measurement of resident CPU model tensors. GPU usage, host working set and shared GPU counters must be interpreted separately. Windows file cache, paging, driver memory and arbitrary future OS eviction behavior prevent a universal physical-residency or complete-erasure guarantee.

A separate signed-candidate sampling run observed a 791,146,496-byte worker working set, 21,456,310,272-byte dedicated GPU counter and 94,371,840-byte shared GPU counter at their sampled maxima. These snapshots can miss peaks. Small driver/staging shared-memory allocations are distinct from model spill; model/KV accounting and arithmetic placement were simultaneously checked by the worker. The earlier fit harness observed 22,886 MiB total dedicated GPU usage including desktop/other GPU processes.

Owned mutable input/output buffers and KV cleanup remain; forced cancellation, crash capture, GPU scratch/driver copies, immutable strings and OS copies cannot all be irreversibly erased. Normal cancellation signals cooperative cleanup and then kills a nonresponsive job after two seconds. Private RSA-4096/ML-DSA-87 keys and trust pins are unchanged; they remain separate DPAPI CurrentUser ciphertexts on A:, excluded from binaries and Git.
